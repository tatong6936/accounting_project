3. Schema Deployment — ปัญหาและวิธีแก้ (9 Iterations)

คำสั่งที่ใช้: cf run-task accounting-srv --command "node srv/deploy-db.cjs" --name "deploy-schema-N"
Iteration 1-2: cds.deploy() delta path — DROP TABLE blocked
Error: "Dropping tables not supported (in artifact: com.demo.timesheet.Projects)"
สาเหตุ: DB มีตารางเก่าจาก project อื่น (timesheet) CDS delta migration ไม่ยอม DROP foreign tables
Iteration 3-5: DROP ด้วย pg.Pool แล้วค่อย cds.deploy()
DROP สำเร็จ แต่ cds.deploy() ใช้ fresh install path → Error: type "nvarchar" does not exist
สาเหตุ: CDS fresh path ออก SQLite-specific DDL types (NVARCHAR, DATE_TEXT, TIMESTAMP_TEXT, NCLOB ฯลฯ)
Iteration 6-8: cds.compile.to.sql() + regex type mapping
เพิ่ม type mapping ทีละตัว: NVARCHAR→VARCHAR, TIMESTAMP_TEXT→TIMESTAMP, TIME_TEXT→TIME, NCLOB→TEXT
แต่ยังขาด SMALLDECIMAL, NBINARY, VARBINARY, BINARY_FLOAT, BINARY_DOUBLE, NDOUBLE, NFLOAT, NBLOB, NLONGSTRING
Iteration 9: ✅ สำเร็จ — Created 7 database objects
เพิ่ม comprehensive type mapping ครบทุก CDS SQLite type alias
เวลา: 17:17:41 — Schema deployed successfully!

Solution สุดท้าย: deploy-db.cjs

Logic หลัก:
  1. อ่าน VCAP_SERVICES หา PostgreSQL credentials + SSL config
  2. DROP ทุก table ที่ไม่ใช่ com_hospital_accounting% ด้วย pg.Pool
  3. โหลด model: cds.compile.to.sql(model)
  4. แปลง SQLite types → PostgreSQL types ด้วย regex (toPostgresSQL())
  5. Execute DDL ผ่าน pg.Pool โดยตรง + CREATE TABLE IF NOT EXISTS

⚠️ ทำไมไม่ใช้ cds.deploy() ตรงๆ
— Delta path: บล็อก DROP TABLE ของ foreign schemas
— Fresh path (ไม่มี cds_model table): ออก SQLite DDL types ที่ PostgreSQL ไม่รู้จัก
→ ต้อง bypass ด้วย cds.compile.to.sql() + type mapping + pg.Pool

4. DB Connection Fix — server.js

ปัญหา: ECONNREFUSED 127.0.0.1:5432

แม้ add "db": "postgres" และ "vcap": { "label": "postgresql-db" } ใน package.json แล้ว CDS 10 ยังคง connect localhost เพราะ VCAP_SERVICES auto-discovery ทำงานตาม kind name vs VCAP label/tag:

  • kind: "postgres" → หา VCAP label "postgres" → ไม่เจอ (label จริงคือ "postgresql-db")
  • VCAP tags: ["relational", "database"] → ไม่มี "postgres"

✅ Solution: Custom server.js

CDS โหลด server.js ที่ root ของ app ก่อน bootstrap จึง inject credentials ตรงๆ:

import cds from '@sap/cds';

if (process.env.VCAP_SERVICES) {
    const vcap = JSON.parse(process.env.VCAP_SERVICES);
    const pgSvc = Object.values(vcap).flat()
        .find(s => s.credentials && (s.credentials.hostname || s.credentials.host));
    if (pgSvc) {
        const c = pgSvc.credentials;
        cds.env.requires ??= {};
        cds.env.requires.db ??= {};
        cds.env.requires.db.credentials = {
            host: c.hostname || c.host,
            port: parseInt(c.port) || 5432,
            user: c.username || c.user,
            password: c.password,
            database: c.dbname || c.database,
            ssl: { rejectUnauthorized: false }
        };
    }
}

export default cds.server;

ผลลัพธ์ใน log:

[cds] - bootstrapping from { file: 'server.js' }
[server.js] PostgreSQL credentials injected from VCAP_SERVICES (postgres-5c194fbb-...:5887)
connect to db > postgres { host: 'postgres-5c194fbb-...', port: 5887, ... }
⚠️ สำคัญ: server.js ต้องอยู่ที่ root ของ deployed app (gen/srv/server.js)
mta.yaml build step จะ copy จาก source root ให้อัตโนมัติ: 
- node -e "require('fs').copyFileSync('server.js','gen/srv/server.js')"
ข้อดีของ approach นี้: credentials อ่านจาก VCAP_SERVICES ทุกครั้งที่ start → ทำงานถูกต้องแม้ rebind service (username/password เปลี่ยน)

6. Ghost Service Error (Known Issue)

Error ที่เห็นทุกครั้งที่ cf deploy

Error detaching services from MTA:
CF-ServiceInstanceNotFound(60004): The service instance could not be found: accounting-db

สาเหตุ: MTA deployment ครั้งแรกลงทะเบียน managed service ชื่อ accounting-db แต่ต่อมาเปลี่ยนเป็น accounting-postgres (existing service) ใน mta.yaml — MTA deployer จึงพยายาม detach service เก่าที่ไม่มีอยู่แล้ว

ผลกระทบ: ไม่กระทบการทำงานของ app — app start สำเร็จก่อน error นี้จะเกิด

Workaround: หลัง app start สำเร็จ abort process ด้วย:
cf deploy -i <operation-id> -a abort
วิธีแก้ถาวร (ยังไม่ได้ทำ): ลบ ghost MTA reference ออกจาก BTP cockpit หรือใช้ cf undeploy accounting --delete-services แล้ว deploy ใหม่ทั้งหมด

7. คำสั่งที่ใช้บ่อย

Deploy App (วิธีเร็ว — แนะนำ)

Build CDS model 
npx cds build --production
Push app โดยตรง (ข้าม MBT + ghost service error) 
cf push accounting-srv -p gen/srv -b nodejs_buildpack

Deploy App (วิธี Full MTA)

npx cds build --production
mbt build -t mta_archives
cf deploy mta_archives/accounting_1.0.0.mtar
หาก ghost service error: cf deploy -i <id> -a abort

Deploy Schema (หลัง deploy app หรือเมื่อ DB binding เปลี่ยน)

cf run-task accounting-srv --command "node srv/deploy-db.cjs" --name "deploy-schema-N"

8. บทเรียนสำคัญ

❌ อย่าทำ

  • ใช้ cds.deploy() กับ PostgreSQL ที่มี foreign tables → ติด DROP TABLE safety
  • ใช้ cds.deploy() fresh path → ได้ SQLite DDL types
  • พึ่ง VCAP_SERVICES auto-discovery ของ CDS เมื่อ service label ไม่ตรง kind
  • รัน cd path && command ใน PowerShell 5.1
  • ใช้ token เก่าหลัง cf deploy (clientsecret เปลี่ยน)

✅ ควรทำ

  • ใช้ cds.compile.to.sql() + regex type mapping + pg.Pool
  • สร้าง server.js inject credentials จาก VCAP_SERVICES
  • ใช้ cf push -p gen/srv แทน MBT เมื่อแก้แค่ code
  • ตรวจ cf env หลัง deploy เพื่อดู clientsecret ใหม่
  • ตรวจ log --recent ก่อน test API

Key Insight: ES Module vs CommonJS ใน CAP

ไฟล์Module Systemเหตุผล
accounting-service.jsESM (import/export)package.json มี "type":"module"
deploy-db.cjsCommonJS (require())นามสกุล .cjs บังคับ CJS แม้ใน ESM package
server.jsESM (import/export)ต้องตรงกับ package type

BTP PostgreSQL Hyperscaler — ข้อควรรู้

  • Port ไม่ใช่ 5432 แต่เป็น 5887
  • SSL จำเป็น — ใช้ ssl: { rejectUnauthorized: false }
  • ทุกครั้งที่ rebind service (cf deploy): username + password เปลี่ยนใหม่
  • VCAP_SERVICES label คือ "postgresql-db" (ไม่ใช่ "postgres") → ทำให้ CDS auto-discovery ล้มเหลว
  • Table ที่ user เก่าสร้าง — user ใหม่อาจเข้าถึงได้ (BTP grant by default) แต่ถ้ามีปัญหา redeploy schema ด้วย user ใหม่
